## Required Project work records

Before modifying this repository or starting a substantial requested investigation, read [Project/README.md](Project/README.md) and [Project/INDEX.md](Project/INDEX.md).

- Create or reuse `Project/<Type><NNN>-<short-title>.md` from `Project/TEMPLATE.md` before implementation. Use the guide's type prefixes and collision-checked IDs.
- Document scope, observable acceptance criteria, dependencies, and a concrete ordered task checklist. Keep the record and index current during implementation, validation, and handoff.
- Explain the technical approach, actual implementation, decisions, affected components, evidence, blockers, and final result. Describe system behavior and interfaces; avoid line-by-line code narration.
- Check only completed tasks. Report failed/skipped validation honestly; never claim completion or user acceptance without evidence.
- Reuse the same record for follow-ups to the same work. Link existing GitHub Issues/PRs and obey repository-specific authorization and review rules; this record does not independently authorize execution.
- Include work-record updates with the related implementation commit. Preserve unrelated content and historical records.
- For updates confined to `Project/*.md` and agent-instruction Markdown, use documentation checks from the guide. No application restart/build, product version bump/tag, or application test run is required solely for these tracking files. Normal requirements apply when runtime/build/application inputs change.
- Keep these work records in English Markdown, including in repositories whose product documentation uses another format. This is a tracking-format exception only.

This section governs the work-record format and tracking-only validation scope. Existing technical, security, execution, and release rules remain applicable outside that scope.
